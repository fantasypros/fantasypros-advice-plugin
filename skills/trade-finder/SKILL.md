# Trade finder

Workflow for showing the user the trades Trade Finder finds, where both sides benefit, as Trade Finder returned them.

**Inputs:** optional constraints from the user (target player/position, player to move, preferred trade partner, players to keep, offers a partner already rejected).

0. **Named target? Find who owns him first.** If the user names a player to acquire, you MUST find which team rosters him BEFORE anything else: call `get_roster` with `all_teams=true` and the selected `league_key` and look for the player on each team's roster. That is exact for the selected league. `get_player_ownership` scans every league the user has synced, not just the selected one, so you MAY use it as a cross-check, but a missing or differently named entry for the selected league never means he is a free agent or unowned — in that case rely on the rosters. The team that owns him is the trade partner — no other team can send him. If he is on the user's own roster, say so instead of proposing a trade; only call him a free agent if no roster in the selected league has him. Never infer a named player's fantasy team from memory or from positional fit. The same goes for every player you propose to acquire, not only ones the user names: take him from a `trade_finder` move (its `summary` says which team sends whom) or from the `players_at_need` of the team you name in `rank_trade_partners`, and never propose acquiring one of the user's own players.
0a. **A trade the user describes comes first.** When the user describes a specific offer, their own or one a partner made them ("he offered his A and B for my X and Y"), and asks whether to take it or how to counter, you MUST call `trade_analyzer` on exactly that trade before anything else. Then state the direction from its result (who gives whom) and its verdict before any counter. A counter is a different trade, so score it too (step 3).
1. **Assess the user's roster.** You MUST call `get_roster`. You MAY call `league_analyzer` for positional context. Position ranks only explain a move ("this fixes your 10th-ranked WR room"). They never choose what to search for, and they never rule a move out: Trade Finder already weighs every team's needs and depth.
1a. **Rank partners only when the user names positions.** When the user says which position they are moving or which they want ("trade a WR for an RB"), you MUST call `rank_trade_partners` with `position_surplus` and/or `position_need`. It returns the other teams ordered by fit, best first, with the ranks behind each score. A viable partner is WEAK at the position the user is selling and STRONG at the position the user wants; recommending a team that is strong at what the user is selling, or thin at what the user wants, is backwards. When step 0 found the owner of a named target, the owner is the partner, so skip this step. When the user names no position, skip it too, and never pick the user's weakest position yourself.
2. **Generate candidates.** You MUST call `trade_finder`.
   - **No position or player named** ("trade suggestions for me", "find me a trade"): the first call MUST have no position filter, neither `position_trade_for` nor `position_trade_away`.
   - **A player to move** ("what can I get if I give up X?"): set `player_trade_away` only. Packages that add other players from the user's roster answer that request; never discard them for including other players.
   - **Otherwise** pass the constraints the user gave (`player_trade_for`, `player_trade_away`, `position_trade_for`, `position_trade_away`, `team_trade_with`; when step 0 found an owner, set `player_trade_for` and `team_trade_with` to that owner). These combine, so a "trade away X to get Y" request is ONE call with both sides set — never two calls, and never just one side.
   - **Players to keep:** when the user says a player is untouchable or must stay, in this message or earlier in the conversation, pass him in `players_to_keep` on every `trade_finder` call. Do not ask for untouchables up front.
   - **Rejected offers:** when the user says a partner rejected an offer, pass it in `exclude_trades` as "<players the user gives> for <players the user gets>", together with any other offer rejected earlier in the conversation (separated by ";").
   - The response echoes `filters_applied`. If it reports that nothing matched, that is a real empty result: say so rather than re-running with fewer constraints and presenting the wider answer as if it matched. A named player with no move, whether the user wants him or wants to trade him away, goes to step 2a. When the response has `close_calls` instead of `moves`, no move gains both teams: present the close calls (step 3).
2a. **A named player with no move, or "balance my trade".** When `trade_finder` returns no move for a player the user wants or wants to trade away (it never suggests players on NFL injured reserve or the PUP list), or the user asks what more to get to balance a trade they describe, build offers yourself. Take outgoing players only from the user's roster, including the player they want to trade away, and incoming players or add-ons only from one partner's roster (`get_roster` with `all_teams=true`). Score each offer with `trade_analyzer` and adjust it until its `two_sided_verdict.fair` is true, using at most four `trade_analyzer` calls. Present one or two offers labeled as offers you built, each with both teams' numbers. If none is fair, present those whose `two_sided_verdict.close_call` is true as close calls; say that none you scored was fair or close only after scoring them. Never end without a scored offer, and never answer "add nothing" without scoring an add-on.
2b. **The partner declined or rejected an offer.** When the user says a partner declined ("he doesn't want to trade") or rejected an offer:
   - The team that declined is the partner of the trade the user is answering, from your previous reply. Name that team; never name a team you did not propose.
   - Never present the rejected trade again, or one that gives that team less for the same players (`exclude_trades` leaves these out).
   - If the team won't trade at all, search other teams: call `trade_finder` with `team_trade_with` for the next two or three `rank_trade_partners` teams, or with no team filter, and leave out the team that declined. If it rejected only that offer, search the same team again with `exclude_trades`.
   - Claim only the searches you actually ran ("I checked Team A and Team B").
3. **Present moves as returned.** Every move `trade_finder` returns gains both teams something; it leaves out the rest and counts them in `moves_filtered`. You MUST present each trade player for player, exactly as returned, with the partner team — 3-for-1 and 3-for-2 packages included. Do not trim, split or combine moves. Any change is a different trade (fewer players, a swapped player, another partner, or an offer you build yourself): you MUST run `trade_analyzer` on it, label it a modified offer, and give its numbers for both teams. When the user asks for a "fair" trade, present only offers whose numbers show neither team losing value, or say that none was found (and offer any close calls, labeled as close calls). A `trade_analyzer` result is fair only when its `two_sided_verdict.fair` is true: never call an offer fair, balanced, realistic or likely to be accepted otherwise, and follow its `say`, which covers both teams. A close call (an entry in `trade_finder`'s `close_calls`, or a `trade_analyzer` result whose `two_sided_verdict.close_call` is true) gains the user and costs the other team at most 0.5%: when nothing fair exists, present it as a close call the other team might accept, with both teams' numbers, and never call it fair or mutually beneficial.
4. **Explain each move from the tool (applies to candidates returned by `trade_finder`, never to a trade the user proposed).**
   - Each move's `summary` says which team sends whom and lists any free-agent pickups or drops Trade Finder's gains count. Say those roster moves when you present the trade ("you also pick up Mike Washington Jr. from free agency"). To re-score a move or quote its exact numbers, call `trade_analyzer` with that move's `trade_analyzer_args` unchanged.
   - Each move carries `position_changes`, one sentence per position it touches. Use them, with the position ranks they quote, to say what the user gains and gives up, and say it plainly when `position_downgrades` lists a position ("you give up QB6 Caleb Williams and get back QB9 Jayden Daniels, a step down at QB"). Never call a move an upgrade at a position it downgrades.
   - Depth charts describe a player's role; they are never a reason to discard a move. A WR at depth 1–3, or an RB or TE at depth 1, is a starter. Before you call an incoming RB, WR or TE an upgrade, a starter or a lead back, you MUST call `get_nfl_depth_charts` for him and state his depth ("RB1 on the Falcons' depth chart").
   - In a dynasty league, run `trade_analyzer` on the trades you present and quote its dynasty change, as the `trade_finder` instructions say.
5. **Answer.** You MUST name concrete trades: present the top 2-3 moves — or every returned move when the user asks for as many as possible — each with a two-sided rationale: what the user gains and why, and who the other team is and why they would accept ("you get X because ...; they accept because ..."). A general plan ("shop a WR for an RB") never satisfies this step. You may answer without a trade only when `trade_finder` returned no moves and no close calls and, for a named player, step 2a found no fair offer or close call: say why, from its error or `moves_filtered` (for example, that the other team would gain nothing). If the user named positions and the top one or two `rank_trade_partners` teams have no moves in the results, call `trade_finder` with `team_trade_with` for them before concluding.

## Data sources
- Rosters, rankings, league standings, and trade evaluations MUST come from the FantasyPros tools above. Do not web-search to check or supplement them, and never let a web result override them. Never infer which fantasy team owns a player from the web or from memory.
- Say how current the data is when it matters: results carry `data_as_of` (date, season, week, and that week's `nfl_week_dates`; "this week" is that week), and `injury_status` news items carry `published`.
- For anything the tools do not cover (for example why a player's role changed), you MAY search the web: prefer fantasypros.com and the most recent sources, skip anything from a previous season, and say where the information came from and when it was published.
